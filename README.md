## 1. 프로젝트 개요

### MAC(Multiply-Accumulate) 연산과 AI에서의 중요성
컴퓨터는 이미지를 시각적 형태가 아닌 2차원 숫자 배열(행렬)로 인식합니다. 입력 패턴과 기준이 되는 **필터(Filter)**를 같은 위치끼리 겹쳐 각 원소를 곱하고(`Multiply`), 그 결과를 모두 누적 합산(`Accumulate`)하면 두 배열의 유사도를 나타내는 점수(Score)를 얻을 수 있습니다.

- **유사도 판별 원리**: 입력 패턴과 필터의 활성 영역이 많이 겹칠수록 MAC 점수가 높게 계산되고, 겹치지 않을수록 점수가 낮아집니다. 두 필터의 MAC 점수를 비교해 더 높은 점수를 얻은 필터의 클래스를 최종 판정 결과로 선택합니다.
- **NPU가 필요한 이유**: `3×3` 필터는 9회의 MAC 연산만 필요하지만, 실제 AI 모델은 수백×수백 크기의 필터를 수천 개씩 적용하므로 이미지 한 장을 처리하는 데 수억 번의 MAC 연산이 수행됩니다. 직렬 처리에 최적화된 CPU는 이러한 대규모 단순 반복 연산을 빠르게 감당하기 어렵기 때문에, 수천 개의 MAC 연산을 동시에 처리(병렬 처리)하는 AI 전용 칩 **NPU(Neural Processing Unit)**가 사용됩니다.

### 개발 환경 및 제약 조건
- **언어**: Python 3.8 이상
- **허용 라이브러리**: 표준 라이브러리(`json`, `math`, `os`, `re`, `time`)만 사용
- **제약 사항**: NumPy, pandas 등 외부 벡터화 라이브러리 사용 금지 (반복문 기반 MAC 직접 구현)

## 3. 구현 요약

### 1) 데이터 구조 (`Matrix2D`) 및 검증 정책
- **2차원 배열 저장/접근**: `Matrix2D` 클래스가 `N×N` 정방 행렬을 2차원 리스트(`list[list[float]]`)로 저장하며, `get(row, col)` / `set(row, col, value)` 메서드로 특정 위치 값을 읽고 쓸 수 있습니다. `3×3`, `5×5`, `13×13`, `25×25`를 포함한 임의의 크기를 지원합니다.
- **모드 1 입력 검증**: 각 줄의 공백 분리 토큰 개수, `float` 변환 가능 여부, 유한수(`math.isfinite`) 여부를 검증해 오류 시 재입력을 유도합니다.
- **모드 2 JSON 스키마·크기 검증**:
  - `patterns` 키(`size_{N}_{idx}`)에서 `N`을 추출해 대응하는 `filters["size_{N}"]` 필터를 매칭합니다.
  - 정방 행렬 여부, 숫자 타입(`bool` 제외·유한수 검사), 필터-패턴 크기 일치 여부를 검증하며, 불일치·스키마 오류가 발생해도 프로그램이 비정상 종료되지 않고 해당 케이스만 `FAIL`과 원인 메시지로 기록합니다.

### 2) 라벨 정규화(표준화) 방식
`data.json`에서는 `filters` 키와 `patterns.*.expected`의 표기 규칙이 서로 다르므로, 프로그램 내부 표준 라벨(`Cross`, `X`)로 정규화합니다.

| 구분 | 원본 값 (`data.json`) | 내부 표준 라벨 |
| :--- | :---: | :---: |
| `filters.size_N` 키 | `"cross"` | `Cross` |
| `filters.size_N` 키 | `"x"` | `X` |
| `patterns.*.expected` | `"+"` | `Cross` |
| `patterns.*.expected` | `"x"` | `X` |

- **표준화 이유**: 원본 문자열(`"+"`, `"cross"`, `"x"`)을 그대로 비교하면 의미가 동일한 라벨도 불일치(`"cross" != "+"`)로 처리됩니다. 데이터 로드 단계에서 `Cross` / `X`로 통일함으로써 점수 매핑, 콘솔 출력, `PASS`/`FAIL` 비교를 단일 기준으로 일관되게 수행합니다. *(새 라벨 추가 시 확장 절차는 [5. 확장 가이드: 새 라벨 추가 절차](#5-확장-가이드-새-라벨-추가-절차) 참고)*

### 3) MAC 연산 구현 개요
NumPy 등 외부 라이브러리 없이 이중 `for` 반복문으로 위치별 곱셈 및 누적 합산(`score = Σ pattern[r][c] × filter[r][c]`)을 직접 구현했습니다.

```python
def mac_2d(pattern: list[list[float]], kernel: list[list[float]]) -> float:
    n = len(pattern)
    total = 0.0
    for r in range(n):
        row_p = pattern[r]
        row_k = kernel[r]
        for c in range(n):
            total += row_p[c] * row_k[c]
    return total
```

### 4) 점수 비교 및 동점 처리 정책 (`epsilon`)
IEEE 754 `float64` 누적 연산에서는 `0.1`, `0.3` 같은 10진 소수의 이진 표현 한계로 미세한 반올림 오차가 발생합니다. 단순 비교(`score_a > score_b`)를 사용하면 수학적으로 동점인 경우에도 오차 방향에 따라 오판정될 수 있으므로 허용오차 기반 비교 정책을 적용했습니다.

```python
EPSILON = 1e-9
```

- `abs(score_a - score_b) < EPSILON` → 동점 (`UNDECIDED` / 모드 1에서는 `판정 불가`)
- `score_a > score_b` → `Cross` (모드 1에서는 `A`)
- `score_b > score_a` → `X` (모드 1에서는 `B`)
- `data.json` 모드에서는 판정(`Cross` / `X`)이 정규화된 `expected`와 일치할 때만 `PASS`, 다르거나 `UNDECIDED`이면 `FAIL`로 처리합니다.

### 5) 보너스 과제 구현
- **시뮬레이터 최적화 (1차원 배열 메모리 접근)**: `Matrix2D.to_1d()`로 `N×N` 2차원 배열을 길이 `N²`의 1차원 배열(Row-major)로 변환하고, `mac_1d()`에서 단일 루프로 연산하여 이중 인덱싱 오버헤드를 줄였습니다. 동일 입력·동일 반복 횟수로 최적화 전(2D)과 후(1D)의 평균 시간(ms), 개선율(%), 결과 정합성(`PASS`/`FAIL`)을 함께 출력합니다.
- **패턴 생성기 (`generate_cross_pattern`, `generate_x_pattern`)**: 크기 `N` 입력 시 `N×N` `Cross`와 `X` 패턴을 자동 생성하며, 모드 1(`gen cross` / `gen x`), 모드 2(`3×3` 성능 분석 샘플), 모드 3(사용자 정의 크기 생성·검증·벤치마크)에서 재활용합니다.

### 4.2 실패 원인 분석 (데이터/스키마 vs 로직 vs 수치 비교)

실패 케이스 3건(`size_5_1`, `size_13_2`, `size_25_1`)을 세 가지 관점으로 분리해 진단했습니다.

1. **수치 비교 및 부동소수점 오차 관점 (직접적 판정 원인)**
   - **`size_5_1`**: `size_5`의 `cross` 필터 중심`(2, 2)` 가중치가 `0.9`, `x` 필터 대각선 9칸이 각각 `0.1`입니다. X 패턴 입력 시 이론 점수는 두 필터 모두 `0.9`로 동점이지만, `float64`에서 `0.1`을 9회 누적 합산하면 `0.8999999999999999`가 되어 `1.11022302463e-16`의 미세한 오차가 발생합니다.
   - **`size_13_2`**: `size_13`의 `cross` 필터 25칸은 각각 `0.3`, `x` 필터 중심`(6, 6)` 가중치가 `7.5`입니다. Cross 패턴 입력 시 이론 점수는 모두 `7.5`이지만 `0.3`을 25회 누적 합산하면 `2.6645352591e-15`의 오차가 발생합니다.
   - **`size_25_1`**: `size_25`의 `cross` 필터 중심`(12, 12)` 가중치가 `4.9`, `x` 필터 대각선 49칸이 각각 `0.1`입니다. X 패턴 입력 시 이론 점수는 모두 `4.9`이지만 `0.1`을 49회 누적 합산하는 과정에서 `1.7763568394e-15`의 오차가 생깁니다.
   - 허용오차 없이 단순 비교(`>`)했다면 부동소수점 오차 때문에 정답과 반대 클래스(`Cross` 또는 `X`)로 오판정되었을 것입니다. `EPSILON = 1e-9` 정책을 적용함으로써 오차에 흔들리지 않고 정확히 동점(`UNDECIDED`)으로 판별했으며, `UNDECIDED`는 `expected`(`Cross`/`X`)와 불일치하므로 판정 규칙에 따라 `FAIL`로 집계되었습니다.

2. **데이터/스키마 관점 (근본적 데이터 설계 원인)**
   - **스키마 및 라벨 규칙**: `data.json`의 모든 6개 패턴과 3개 크기 필터는 행·열 크기(`5×5`, `13×13`, `25×25`)가 정확히 일치해 스키마/크기 불일치로 인한 `FAIL`은 0건입니다. 또한 `filters`의 `"cross"`/`"x"`와 `expected`의 `"+"`/`"x"` 차이는 **라벨 정규화**로 해소되어 정상 케이스 3건(`size_5_2`, `size_13_1`, `size_25_2`)이 모두 `PASS`로 판정되었습니다.
   - **필터 가중치 편향**: 동점이 발생한 근본 원인은 **비정답 필터의 중심 단일 셀 가중치**(`size_5` cross 중심 `0.9`, `size_13` x 중심 `7.5`, `size_25` cross 중심 `4.9`)가 **정답 필터 전체 셀의 가중치 합**(`0.1×9=0.9`, `0.3×25=7.5`, `0.1×49=4.9`)과 정확히 같도록 데이터가 설계되었기 때문입니다. 중심 1픽셀만 겹쳐도 정답 패턴 전체가 겹친 점수와 같아지므로 필터 변별력이 상실됩니다.

3. **로직 관점 및 개선 방향**
   - `size_5_2`(8.9 vs 0.1), `size_13_1`(0.3 vs 14.7), `size_25_2`(52.9 vs 0.1)에서 MAC 점수가 이론값과 일치하므로 MAC 누적 연산과 판정 분기 로직에는 결함이 없습니다.
   - 실패 케이스를 개선하려면 `epsilon` 비교 정책을 제거하는 대신, **필터 가중치 스케일 정규화**(필터별 총 가중치 합 통일 또는 중심 단일 픽셀 가중치 편향 제거)처럼 데이터/필터 설계를 보정하는 것이 올바른 해결책입니다.

### 4.3 성능 분석 및 시간 복잡도 `O(N²)` 해석

I/O 시간을 제외하고 순수 MAC 연산 함수 호출 구간만 각 크기별로 **100회 반복**(최소 기준 10회 충족 및 측정 안정성 확보) 측정하여 평균 시간(ms)을 산출했습니다. *(실측 시간은 실행 환경에 따라 달라질 수 있습니다.)*

| 크기 (`N×N`) | 평균 시간 (ms) | 연산 횟수 (`N²`) | `3×3` 대비 연산량 배수 | `3×3` 대비 실행 시간 배수 |
| :---: | :---: | :---: | :---: | :---: |
| `3×3` | `0.000447` | `9` | `1.00×` | `1.00×` |
| `5×5` | `0.000889` | `25` | `2.78×` | `1.99×` |
| `13×13` | `0.004409` | `169` | `18.78×` | `9.86×` |
| `25×25` | `0.014669` | `625` | `69.44×` | `32.82×` |

- **시간 복잡도 `O(N²)` 근거**: `N×N` 크기의 입력 패턴과 필터에 대해 바깥 루프(`N`회)와 안쪽 루프(`N`회)를 중첩 실행하며 모든 원소 `(r, c)`를 한 번씩 방문해 곱셈 1회·덧셈 1회를 수행합니다. 총 연산 횟수가 정확히 `N²`에 비례하므로 시간 복잡도는 **`O(N²)`**입니다.
- **연산 횟수와 실측 시간의 연결**:
  - `3×3`(9회)이나 `5×5`(25회)처럼 `N`이 작을 때는 순수 산술 연산 외에 Python 함수 호출·루프 진입 같은 고정 오버헤드 비중이 커서 연산량 증가율(`2.78×`)보다 실행 시간 증가율(`1.99×`)이 완만하게 나타납니다.
  - 반면 `N`이 커질수록 이중 루프 내부의 `N²` 연산 비용이 전체 시간을 지배합니다. `5×5 → 13×13` 구간에서는 연산량이 `6.76×`(`169/25`) 늘 때 실행 시간이 `4.96×` 늘었고, `13×13 → 25×25` 구간에서는 연산량이 `3.70×`(`625/169`) 늘 때 실행 시간도 **`3.33×`** 증가해 이론적 `O(N²)` 추세에 수렴함을 확인할 수 있습니다.
- **NPU 관점 시사점**: `25×25`만 되어도 연산량이 `3×3`의 `69.4배`로 급증합니다. 수백×수백 크기의 필터를 수천 개 처리하는 실제 AI 추론에서는 직렬 CPU 반복문의 한계가 명확하므로, 대량의 MAC 연산을 병렬 수행하는 NPU 하드웨어가 필수적입니다.

### 4.4 보너스: 메모리 접근 최적화 성능 비교 (2D vs 1D)

동일 입력과 동일 반복 횟수(100회) 기준으로 2차원 배열(`mac_2d`)과 1차원 평탄화 배열(`mac_1d`)의 성능을 비교하고 결과 일치 여부를 검증했습니다.

| 크기 (`N×N`) | 2D 평균 (ms) | 1D 평균 (ms) | 개선율 (%) | 결과 검증 |
| :---: | :---: | :---: | :---: | :---: |
| `3×3` | `0.000447` | `0.000257` | `42.56%` | `PASS` |
| `5×5` | `0.000889` | `0.000574` | `35.39%` | `PASS` |
| `13×13` | `0.004409` | `0.003582` | `18.76%` | `PASS` |
| `25×25` | `0.014669` | `0.014270` | `2.72%` | `PASS` |

- **정합성 검증**: Row-major 평탄화 순서가 2차원 중첩 순회 순서와 동일하므로 모든 크기에서 2D MAC과 1D MAC의 점수가 일치(`PASS`)합니다.
- **최적화 효과**: 이중 반복문과 이중 인덱싱을 길이 `N²`의 단일 루프·단일 인덱싱(`pattern_1d[i]`)으로 단순화해 전 구간에서 **2.72% ~ 42.56%**의 실행 시간 단축을 확인했습니다. 특히 `3×3`·`5×5`처럼 크기가 작을수록 외부 루프 및 행 검증 오버헤드 제거 효과가 크게 나타나며, `25×25`에서도 1D 방식이 더 빠른 실행 시간을 유지했습니다. 시간 복잡도는 동일하게 `O(N²)`이지만 루프·인덱싱 상수 계수가 감소해 실질적 성능이 개선되었습니다.

## 5. 확장 가이드: 새 라벨 추가 절차

현재 시뮬레이터는 2개의 표준 라벨(`Cross`, `X`)을 지원합니다. 새로운 패턴 라벨(예: `Circle`, 필터 키 `"circle"`, `expected` 표기 `"o"`)을 추가할 때는 아래 **4단계 순서(정규화 매핑 확장 → 코드 로직 확장 → `data.json` 업데이트 → 테스트 케이스 추가 및 검증)**에 따라 확장합니다.

### 1단계: 라벨 정규화 함수 확장 (`main.py`)
외부 입력 표현(`filters` 키, `expected` 값)을 새 내부 표준 라벨(`Circle`)로 변환할 수 있도록 정규화 함수를 먼저 확장합니다.

- `normalize_filter_key(raw_key)`: 새 필터 키(`"circle"`) → `"Circle"` 매핑 추가
- `normalize_expected_label(raw_label)`: 새 정답 표기(`"o"`, `"circle"`) → `"Circle"` 매핑 추가

```python
FILTER_LABEL_MAP = {
    "cross": "Cross",
    "x": "X",
    "circle": "Circle",  # 새 필터 키 매핑 추가
}

EXPECTED_LABEL_MAP = {
    "+": "Cross",
    "cross": "Cross",
    "x": "X",
    "o": "Circle",       # 새 expected 라벨 매핑 추가
    "circle": "Circle",
}
```

### 2단계: 필터 검증 및 다중 라벨 판정 코드 변경 (`main.py`)
정규화 매핑 추가 후, 새 라벨이 로드·검증·점수 비교·출력 단계 전반에서 누락 없이 처리되도록 코드를 수정합니다.

1. **필터 로드 검증 확장 (`load_and_validate_filters`, `run_json_mode`)**:
   - 필수 표준 라벨 집합을 `REQUIRED_LABELS = ("Cross", "X", "Circle")`로 확장하여, 모든 `size_N` 필터에 새 라벨 필터가 존재하는지 검증합니다.
   - 필터 로드 완료 출력 및 케이스별 점수 출력 루프가 `REQUIRED_LABELS`를 순회하도록 변경합니다.
2. **다중 점수 비교 정책 일반화 (`compare_scores`)**:
   - 2개 점수 비교(`score_a`, `score_b`)를 라벨별 점수 딕셔너리(`scores: dict[str, float]`) 비교로 확장합니다.
   - 모든 라벨 필터에 대해 `mac_2d`(및 `mac_1d` 정합성 검증)를 수행한 뒤, 1위 점수(`top1`)와 2위 점수(`top2`)의 차이가 `abs(top1 - top2) < EPSILON`이면 `UNDECIDED`, 아니면 1위 라벨을 반환합니다.
3. **보너스 패턴 생성기 확장 (선택)**:
   - `generate_circle_pattern(n)` 함수를 추가하고, 모드 1 단축 입력(`gen circle`) 및 모드 3 자가 검증에 연결합니다.

### 3단계: `data.json` 필터 키 및 패턴 스키마 업데이트
코드가 새 라벨을 수용할 준비가 되면 `data.json` 데이터를 업데이트합니다.

1. **`filters` 섹션 업데이트**: `size_5`, `size_13`, `size_25` 각각에 `"circle"` 키와 해당 크기의 `N×N` 2차원 숫자 배열을 추가합니다.
2. **`patterns` 섹션 업데이트**: 기존 `size_{N}_{idx}` 네이밍 규칙을 따라 새 패턴 항목(예: `size_5_3`, `size_13_3`, `size_25_3`)을 추가하고, `input`(`N×N` 배열)과 `expected`(`"o"`)를 기입합니다.

```json
{
  "filters": {
    "size_5": {
      "cross": [ "...5x5..." ],
      "x": [ "...5x5..." ],
      "circle": [ "...5x5..." ]
    }
  },
  "patterns": {
    "size_5_3": {
      "input": [ "...5x5..." ],
      "expected": "o"
    }
  }
}
```

### 4단계: 테스트 케이스 추가 및 회귀 검증
마지막으로 새 라벨의 정상 동작과 기존 기능의 회귀 여부를 단계별로 검증합니다.

1. **정상 분류 테스트 (`PASS` 확인)**: 크기별(`5×5`, `13×13`, `25×25`) 새 라벨 패턴 입력 시 `Circle` 점수가 최고 점수로 계산되어 `판정: Circle | expected: Circle | PASS`가 출력되는지 확인합니다.
2. **동점 및 예외 케이스 테스트 (`FAIL` 처리 확인)**:
   - 새 라벨과 기존 라벨의 점수 차이가 `1e-9` 미만인 동점 케이스에서 `UNDECIDED` / `FAIL`이 정상 기록되는지 확인합니다.
   - 미등록 `expected` 값, 새 필터 키 누락, `N×N` 크기 불일치 케이스에서 프로그램이 비정상 종료되지 않고 케이스 단위 `FAIL`과 원인 메시지가 출력되는지 확인합니다.
3. **기존 케이스 회귀 및 최적화 정합성 확인**:
   - 기존 6개 테스트(`size_5_1` ~ `size_25_2`)의 `PASS`/`FAIL` 결과가 의도치 않게 변경되지 않았는지 확인합니다.
   - 새 라벨 필터에 대해서도 2D MAC과 1D MAC 결과가 일치(`PASS`)하고 `O(N²)` 성능 추세가 유지되는지 확인합니다.
